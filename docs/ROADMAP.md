# Starry List 开发路线图

维护者：yoli。更新日期：2026-10-15（Asia/Shanghai）。[需求池](PRODUCT_BACKLOG.md) 是详细需求与状态的唯一权威来源；本文件展示方向与推荐顺序，不是交付日期或开发授权。

## 产品愿景

**美观、舒适、方便。** Starry List 希望成为一款能长期留在 Windows 桌面、帮助用户轻松安排生活与工作的日历清单。它强调轻量、易用、精致的视觉体验和低认知负担，本地优先、保护隐私、不干扰正常工作，并为长期维护与扩展留下空间。

Windows 是当前主要平台，未来考虑 macOS。桌面驻留是待验证的产品方向，不能把普通窗口关闭置顶当作已经实现。

## 推荐下一轮顺序（建议，不是开工清单）

1. **下一轮建议仅做三个小范围 UX 修复。** 先 SL-002：同一时间仅一个新增区，空白失焦、再次点击加号和 Esc 可收起，切换范围/视图清理空输入，非空草稿不静默丢失。再 SL-019：总览与专注真实任务行增加「···」编辑/删除入口，复用已有确认、删除和撤销，不重复数据库功能。最后 SL-004-A：让两种视图的快速新增文字与任务标题协调，以约 15–16px 为设计参考，占位符不缩小，窄屏无溢出。这三项共享任务行和快速新增回归，可同轮实现，但当前只是建议，未开工。
2. **完成 SL-001 / SL-002 及本轮子项的用户验收与边界回归。** SL-001 / SL-002 保留 In Review，直到各自条件实际满足。检查新增草稿、输入法、保存失败、删除撤销和宽窄窗口。SL-004-A 的验收单独记录，不提前关闭全局字号父需求；代码提交和自动化通过均不能代替用户确认。
3. **小型修复体验稳定后再开始 SL-003 大范围透明视觉优化。** 与 SL-004 的整体字号层级共同评审；全局字号设置为独立后续范围，不夹带进 SL-004-A。随后处理 SL-005，依赖字体层级和顶部背景方向明确，避免重复调整布局。
4. **SL-006 只先做研究 A；SL-007 / SL-008 可独立评估。** 不让尚未验证的 Explorer 集成阻塞可控的日程改进。若 SL-008 定位到真实性能缺陷，记录理由后可以提高优先级。
5. **SL-009 在驻留交互方案明确后评估；其余 Idea 按用户需求升级。** 云端和跨平台必须先确认维护成本与隐私边界。SL-006、SL-007、SL-008 保持既有状态，研究/开发均需后续明确请求；SL-007 需复用 SL-002 范围切换草稿策略，SL-008 先定位根因再决定动画。

## 进度维护

新反馈先查重并更新需求池，再同步本页阶段摘要。开始实现、测试、用户验收、发布分别记录；In Review 不能因测试通过自动变成 Done。没有创建大量 Issues：未来仅为进入实际开发的需求按同一 SL ID 关联 Issue / PR。
